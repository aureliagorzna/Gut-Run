# Decision Log: Gut Run (Variant A)

Why things are built the way they are. For setup, known issues and next steps see [README.md](README.md).

---

## 1. Rendering: plain `<canvas>`, not DOM

- **Why canvas:** one draw loop and one source of truth for game state, so I have full control over what is drawn each frame. I have used canvas in earlier projects, so I could spend my time on the game instead of the tooling.
- **It also unlocks pixel-based collision** (see section 3), which would be awkward with DOM elements.
- **Trade-off:** no free hit-testing. CTA and replay buttons are tested manually in canvas coordinates.
- **Exception:** the mute toggle is a real HTML `<button>` on top of the canvas (accessible label, easy to style), not something drawn on the canvas.

## 2. Layout and viewport scaling

- **Fixed logic size.** All game code works in the design's 360 × 640 space. Assets are exported at 2x, so every image is drawn at 50% of its pixel size (`img.width / 2`).
- **Scaling is done in CSS, by width.** The canvas always takes 100% of the screen width, and its height follows from the 9:16 ratio. Pointer events are converted back to canvas space with `getBoundingClientRect()`, so clicks land correctly at any size.
- **Tall, narrow screens.** If the screen is much taller than 9:16, there is leftover space below the game. `body` uses the same navy as the game background (`#0B1E49`), so that area looks like part of the ad instead of an empty strip.
- **Scope.** This is a mobile ad, so I optimised for phones. Desktop and tablet can look stretched. With more time I would add a tablet layout that reveals more of the tunnel instead of scaling up.

## 3. Collision

**Tunnel walls (pixel-based).**
- An off-screen canvas mirrors `gameplay.png` every frame, at the same position and scale as the visible one.
- Only the small area around the player (11 × 11 px) is read with `getImageData`. If any pixel inside the player's circle is transparent (alpha ≤ 128), the player has left the tunnel.
- This way the walls always match the artwork exactly, with no hand-authored path data.
- Leaving the canvas at the top or bottom also counts as a hit.

**Player: circle.** Radius 5 px at the sprite's centre. That is much smaller than the visible poo on purpose, so near-misses never feel unfair.

**Obstacles: rectangles at 60% of the sprite size.**
- Rectangles suit the long text obstacles, and the hitboxes are already shrunk, so round hitboxes would not change how the game feels.
- The check is circle-vs-rectangle and supports rotated obstacles.

**Why so forgiving?** Ad games should be easy and fun. Both values are single constants and easy to change (see the tuning table in the README).

## 4. Gameplay feel

| Choice | Reason |
|---|---|
| **Tap = short hop, hold = keep rising** | Plain Flappy-style tapping gets tedious. Holding makes it comfortable on a touchscreen. |
| **Short no-fall pause (300 ms) after releasing** | Makes the release smoother instead of dropping instantly. |
| **Only ~30% of the gameplay texture is used** | 15 obstacles spread over the whole texture would be too sparse and the ad too long. A shorter run is also easier. |
| **Obstacles scaled to 0.3–0.5** | Most had to shrink beyond the planned 50% to stay avoidable. |
| **Hand-placed obstacles, each used exactly once** | Placement is tuned by hand so every section has a passable gap. |
| **"READY" for 1 s after the first tap** | Gives the player a moment before the tunnel and music start. |
| **Bacteria pop in when they enter the screen, then pulse** | Draws attention to them and keeps the tunnel lively. |

## 5. Game loop and frame rate

- **Fixed 60 fps game speed.** The game logic is adjusted so it always runs at the speed of 60 fps, whatever the screen's refresh rate. Scroll speed, gravity and jump speed therefore feel the same on 60, 90 and 120 Hz phones.
- **Why:** my speeds are defined per frame, so without this the game would run twice as fast on a 120 Hz screen, which changes how hard it is. Obstacle spacing and hitboxes were tuned at 60 fps, so keeping that speed keeps the game fair everywhere.

## 6. Animation

- **Written with AI.** All animation code (easing, endcard entrances, bacteria pop-in and pulse, "READY" text) was generated by AI. Writing it by hand would have taken far too long. I read it, understand what it does, and kept it short and controlled (see the AI note in the README).
- **Plain canvas, no library.** The animations use two easing functions (`easeOutBack`, `easeOutCubic`) instead of GSAP. GSAP was allowed, and learning it is my next step.
- **Time-based endcards.** Each element has its own start delay, driven by `performance.now()`, so the stagger looks the same at any frame rate.
- **What animates.** Fail endcard: elements slide and scale in, and the bacteria rotate in one after another. Win endcard: bubble, poo, confetti, headline and CTA pop in as a sequence.

## 7. Audio

- Sounds are plain `Audio` objects, controlled with `.play()` and `.pause()`.
- **Autoplay rules:** nothing plays until the first tap. Background music starts right after the "READY" moment.
- **`currentAudio` set:** tracks which sounds are active. It lets `visibilitychange` pause and resume exactly those sounds, and it is cleared on every view switch so nothing from a previous screen is resumed by mistake.
- **Clean replay:** replaying pauses every sound and rewinds it to 0, so sounds never stack or double up.
- **Crash sound:** the fail endcard appears 1.2 s after the hit, so the crash sound can be heard first.
- **Mute toggle:** sets `muted` on all audio. Its `pointerdown` does not bubble to the canvas, so muting never counts as a jump.
- **Safari/iPhone bug I fixed:** originally the loader waited for every file, including audio, before starting the game. iPhone Safari only loads audio after a tap, so the game never finished loading and showed a blank screen. I changed the loader so only images are required, and audio is loaded and unlocked after the first tap.

## 8. Click-out

- Uses the required `window.clickTag || 'https://example.com/landing'`.
- Both CTAs open the landing page with `window.open(clickTag, "_blank")` when tapped.

## 9. Assets and weight

- Assets are used as exported and not redrawn.
- Total weight (assets, game and docs) is about 2.5 MB, below the 3 MB limit, so I **did not compress anything**.
- All images and sounds are preloaded before the game appears, so nothing pops in during play.

## 10. Code organisation

- One `script.js`, split into sections by banner comments: settings, assets, input, drawing, collision, obstacles, game state, game control.
- Functions that do similar things sit together to make navigating the file easier.
